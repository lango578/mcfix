# 安全设计说明

为什么代码写成这样，方便你审计或二次开发时判断风险边界。

---

## 一、信任模型

| 角色 | 能做什么 | 不能做什么 |
|---|---|---|
| 玩家（持链接） | 提交反馈、上传崩溃报告、触发一次验证、查看自己工单的进度、下载"分析结果里认定他缺"的 MOD | 不能指定要执行什么修复动作、不能看到别的工单、不能读到任何服务器内部信息、不能拿下载接口当文件浏览器、找不到也进不去管理后台 |
| 面板（宝塔这台） | 决定跑哪些预定义配方、下发参数、把 MOD 文件发给玩家 | 不能在 MC 机器上执行任意命令 |
| MC 侧 Agent | 执行白名单配方、采集只读诊断数据、把服务端 mods 目录里的文件传上来 | 不能执行面板传来的任意命令；不认识的 code 直接拒绝 |
| 管理员 | 全部操作，含手动执行配方、批准高风险动作、上传 MOD | — |

**核心不变量：面板被攻破 ≠ MC 机器被攻破。** 攻击者最多能让服务端重启几次（还有每小时配额），拿不到 shell。

### 两个入口的隔离（`src/ConsoleAuth.php`）

玩家反馈界面和管理后台是两个独立入口，隔离手段逐条列出：

| 手段 | 实现 |
|---|---|
| 入口分离 | 玩家侧只有 `?r=feedback&t=...`；后台是配置里的随机私有路径，安装时生成 |
| 路径保密 | 后台路径形如 `console-<16位随机>`；`?r=admin` 返回不带任何信息的 404 |
| 会话隔离 | 会话名不同（`mcfix_console` vs `mcfix_sid`），互不读取 |
| Cookie 属性 | 两个会话都用 `HttpOnly` + `SameSite=Lax` + HTTPS 下 `Secure`（`mcfix_start_session()`） |
| CSRF 隔离 | 后台用自己的令牌（`console_csrf`），不复用玩家侧的 |
| 前端不互链 | 玩家页面没有任何指向后台的链接；未登录时后台只显示"访问验证"，不透露内部信息 |
| IP 白名单 | `admin.ip_allow`，支持单 IP / 通配 / CIDR，留空则不限制（建议填） |
| 失败锁定 | 15 分钟内 6 次失败即锁定，只按来源 IP 计数；`admin.ip_allow` 白名单里的地址不受锁 |
| 会话指纹 | 会话里存"密码哈希 + 后台路径"的指纹，改密码或换后台路径后，其它设备的会话立刻失效 |
| 无网页找回 | 忘记口令只能用 `php bin/mcfix.php reset-password`，网页端没有重设入口 |

> **关于失败锁定为什么不再用全局计数**（1.10.4 改的，别改回去）：
> 以前除了按 IP 数，还有一个全局计数，到 6 就把**整个后台**锁上 ——
> 管理员自己也被关在门外，连登录表单都看不到。攻击者每 15 分钟重放 6 次
> 就能**永久**把管理员锁死。这是拿可用性换安全，而且换错了方向：
> 要防的是"某个来源正在爆破"，不是"全世界都在爆破"。
> 按 IP 锁已经足够（换个 IP 要从头再数），白名单免锁则保证管理员
> 不会被自己的自动化脚本误伤。

关于 cookie 的 `path`：早先的版本想用"cookie 只覆盖后台私有路径"来做隔离，但后台地址是
`/index.php?r=<path>` 形式，浏览器发请求时路径是 `/index.php`，跟 cookie 的 `path` 根本对不上，
结果就是登录后立刻又变回未登录。现在两个会话的 `path` 都是站点基准目录，
隔离靠不同的会话名（外加独立域名时天然同源隔离）实现。

注意：路径保密只是"减少暴露面"，真正拦住人的是口令强度 + IP 白名单 + 失败锁定这三样。
部署时请至少做到前两样。

## 二、修复配方白名单（`src/Recipe.php`）

只有这些 code 是合法的，且 `params` 逐项做类型校验：

| code | 通道 | 参数 | 风险 | 对应动作 |
|---|---|---|---|---|
| `whitelist_add` | 面板 RCON | `player`(3-16 位 `\w`) | 中 | `whitelist add <player>` |
| `unban_player` | 面板 RCON | `player` | 高 | `pardon <player>` |
| `kick_player` | 面板 RCON | `player` + `reason`(≤80，去控制字符) | 中 | `kick <player> <reason>` |
| `clear_self_items` | 面板 RCON | `player` | 高 | `clear <player>` |
| `save_world` | 面板 RCON | — | 低 | `save-all flush` |
| `reload_plugins` | 面板 RCON | — | 中 | `reload confirm` |
| `unmute_player` | 面板 RCON / Agent | `player` | 中 | `unmute <player>`（禁言来自插件，原版没有） |
| `restart_server` | Agent | — | 高 | 按 `guard` 配置重启（`systemctl` / `screen` / `tmux` / 自定义） |
| `backup_world` | Agent | — | 低 | `tar -czf` 打包存档 |
| `monitor_server` | Agent | — | 低 | 只读体检（进程/端口/磁盘），人工触发，系统不会定时调用 |
| `pull_mod` | Agent | `component`（受限字符集） | 低 | 在服务端 `mods/plugins` 里找文件并上传到站点 |

关键点：

1. **Agent 侧 `run_recipe()` 是一个 `switch`，default 分支直接返回失败。** 面板下发 `rm -rf /` 也没用
2. 参数校验在面板侧（`Recipe::validateParams`）和 Agent 侧各做一次，玩家输入永远先过校验
3. `guard.restart_cmd` / `start_cmd` 这类自定义命令只能由管理员在后台配置，玩家碰不到
4. 每台服务器可以逐项关掉配方（后台的复选框），VIP 服可以只留"只诊断"

## 三、签名令牌（`src/Token.php`）

令牌是 `HMAC-SHA256(payload) + payload` 的自包含格式，不需要存储：

| 用途 | scope | 签名密钥 | 有效期 | 可吊销 |
|---|---|---|---|---|
| 玩家公开链接 | `f` + nonce=`share` | 每台服务器独立的 `share_secret` | 30 天 | 后台点「重新生成」即让旧链接失效 |
| 工单链接 | `f` + 工单 nonce | 全局 `hmac_secret` | 24 小时 | 管理员点「重置反馈链接」 |
| 页内验证 | `v` + 随机 nonce | 全局 `hmac_secret` | 30 分钟 | 每枚令牌用过即废（但可反复领取新令牌，见下） |
| MOD 下载 | `d` + 文件名 | 全局 `hmac_secret` | 7 天 | 改文件名/换服务器无法复用 |
| Agent 令牌 | `a` | 全局 `hmac_secret` | 长期 | 后台重新生成 |

设计考虑：

- 令牌里绑定 `feedback_id` + `server_id`，无法跨工单或跨服务器使用
- 公开链接用每服务器独立密钥，轮换它不会影响 Agent 令牌和工单链接
- 验证令牌的 nonce 记在文件缓存里，重复使用会被拒绝（防重放刷诊断）。
  但要说清楚：每枚令牌是"用过即废"，不等于一个人只能验证一次 ——
  `progress` 接口每次都会下发一枚新的可用令牌，所以持有工单链接的人可以反复触发诊断。
  真正的闸门是按来源 IP 的限流（默认 40 次/小时，`feedback.verify_per_hour`）。
  令牌本身不可伪造（HMAC），所以这不是绕过鉴权的问题，而是"不要把限流说成一次性"。
- 校验时会把全局密钥与所有服务器的 `share_secret` 都作为候选，因此密钥轮换期间旧令牌有短暂的兼容窗口

## 四、限流与风控

| 位置 | 规则 | 实现 |
|---|---|---|
| 提交反馈 | 每 IP 每小时 5 条 | `Rate::hit()`，文件桶 + flock |
| 触发验证 | 每 IP 每小时 40 次 | 同上 |
| 取回 MOD 文件 | 每 IP 每小时 20 次 | 同上 |
| Agent 轮询 | 每服务器每小时 900 次 | 同上（正常 8 秒一次 = 450 次） |
| 后台登录 | 失败 6 次锁 15 分钟 | 同上 |
| 自动修复 | 单工单最多 2 次 | `automation.max_fix_attempts` |
| 重启服务端 | 每服务器每小时最多 3 次 | `guard.max_restarts_per_hour` |
| 连续失败 | 3 次熔断为"仅诊断" | `automation.circuit_breaker_failures` |

为什么限流用文件而不是数据库：刷接口时 SQLite 会频繁拿写锁，用文件桶可以完全不碰数据库。
桶文件按时间窗口分片，`Rate::gc()` 在 cron 里清理。

## 五、客户端日志的安全处理

玩家上传的日志是不可信输入里最危险的一类：几百 KB 的任意文本，还是从公网传上来的。
处理约束如下：

| 风险 | 处理方式 |
|---|---|
| 超大文件打满内存 | 单文件上限 512 KB，超过直接拒绝；再大就只保留头尾各 256 KB（`ClientLog::MAX_BYTES = 256 KB`） |
| ReDoS（正则回溯爆炸） | 单行截断到 600 字符、总行数截断到 6000 行；所有特征正则都是简单字符类，没有嵌套量词 |
| 二进制 / 编码炸弹 | 先探测 UTF-16 / GBK 并转成 UTF-8；剔除 NUL 与控制字符 |
| 路径穿越（日志里写文件名） | 日志内容只被解析，从不用于拼接任何文件路径 |
| 日志里夹带指令 | 解析结果只作数据；给玩家的文案全部来自服务端知识库，日志内容只以 `e()` 转义后展示 |
| 通过日志套取服务端信息 | 玩家侧只返回"跟他自己有关"的字段（版本、加载器、MOD 名），不返回服务端 MOD 清单、内部路径、可疑包名 |
| 从反馈页读到服务端连接地址 | 玩家侧一律只显示「代号・名字」（`server_public_label()`），不出现 `host` / `port`。见下面「反馈页不暴露连接地址」 |
| 拿真实日志做社工素材 | 原始日志只对管理员可见（后台工单详情，展示时截断到 20000 字符） |
| 原文无限期留存 | 归档满 `feedback.log_retention_days` 天（默认 30）后由 cron 清空 `client_log` / `client_log_name`，只清原文、保留结论 |

### 反馈页不暴露服务端连接地址（1.13.1 起）

反馈页曾经把每台服务器的 `host:port` 直接印给玩家看：服务器状态卡片一行、
「出问题的服务器」下拉框一行；匿名可调的 `?r=api&action=bootstrap` 也把
`host` / `port` 放在 JSON 里返回。

这等于把 MC 服务端的**可直连地址**公开给任何拿到反馈链接的人。拿到地址之后
扫端口、打 DDoS、绕过白名单尝试直连都从这里开始，而反馈链接是要发到群里给
玩家点的，扩散范围不可控。地址属于连接信息，不是玩家需要知道的东西。

现在的规则：

| 位置 | 显示什么 |
|---|---|
| 玩家反馈页（状态卡片、下拉框） | 「代号・名字」，例如 `S1・生存服 1.20.1`。代号来自 `servers[].code`，留空则只显示名字 |
| `?r=api&action=bootstrap` | 只回 `id` / `code` / `name` / `label`，**没有** `host` / `port` |
| `?r=api&action=ping` | 只回 `online` / `players` / `max`。原来回的 `message` 在失败时是 `stream_socket_client()` 的原始错误，里面带着连接目标，已去掉 |
| `feedback.diagnosis` 这一列 | 只存 `id` / `code` / `name` / `label`，不存 `host` / `port`（这一列是工单数据源，将来若加"把诊断原文给玩家看"的入口，地址不会跟着漏） |
| 管理后台服务器配置页 | 仍然显示完整地址，管理员核对用户面板配置时需要它 |

`tests/run.php` 里有两条断言盯着这件事：`server_public_label()` 的行为，
以及玩家可达的三个文件（`views/player-form.php`、`views/player-ticket.php`、
`public/controllers/api.php`）里**不再出现** `host` / `port` 的取值写法。
后者是源码级守卫 —— 模板的输出行为没法直接用断言覆盖，只能盯写法。

### 多台服务器时，专属链接锁不住服务器（1.13.1 起）

服主有多台服时，每台各有一条公开反馈链接。链接以前只是把下拉框**默认选中**
那一台，选项里仍然列着其他所有服，提交时后端也只看表单值。

于是把 A 服的链接发到 A 服群里，任何人提交时都能把服务器改成 B 服，系统就真去连
B 服做诊断、甚至执行修复。这不算越权（B 服也是服主自己的服），但会消耗 B 服的
风控配额（重启配额按 `server_id` 计），工单也记到 B 服名下，服主查后台会误判。

修法分两层：

| 层 | 做什么 |
|---|---|
| 前端 | A 服的链接进来时，下拉框只列「不涉及服务器」+ A 服 |
| 后端 | 提交时用 `resolve_locked_server_id()` 复核：令牌解出的那台 > session 里记的那台 > 不锁定 |

**为什么必须有 session 这一层**：只有令牌挡不住"故意不带令牌"的绕法 —— 拿着
A 服链接的人手工构一个不带 `share_token` 的 POST、`server_id` 写成 B 服，后端就
没有任何依据区分他和"从首页手选 B 服"的正常玩家。

两个必须保留的例外：「不涉及服务器」（空值）在锁定时仍然放行（客户端崩溃跟是哪台服
无关），以及锁定的服已从配置删掉时不当成锁定。

已知边界：玩家禁用 cookie 时拿不到 session，退化为修复前行为，不报错。

### 日志原文的留存期（1.12.4 起）

崩溃报告里含玩家的 Windows 用户名、显卡型号、游戏 ID、服务器地址。在 1.12.4 之前
没有任何东西删过它：全项目唯一的 `DELETE` 只作用于 `client_issues`，工单和
日志永久保留。而邮箱一直有清理机制（`TicketMail::purgePlayerEmail`），
这个不对称是漏的，现在补上了。

安全边界（`tests/run.php` 里有对应断言盯着）：

- 只清 `status = 'closed'` 的工单。`resolved` 或进行中的工单可能还要重新分析，
  原文删了就分析不了 —— 有一条负向对照专门守这个边界。
- `log_retention_days = 0` 表示关闭该功能，一条都不动。
- 已经清过的（`log_purged_at` 非空）不重复处理。
- 清理记入事件流（`log.purged`），玩家侧可见，不是"日志莫名其妙不见了"。

`php bin/mcfix.php cron` 的输出里会报本次清了几条（`清理日志原文 N`）。

### 我们自己的日志里不写凭据

上面讲的都是玩家日志。我们自己产生的日志同样是泄露面 —— 它们会被备份、
被日志采集服务收走、被顺手 `cat` 出来。三个已经处理掉的地方：

| 位置 | 问题 | 处理 |
|---|---|---|
| nginx access log | 反馈链接的签名令牌在查询串里（`?r=feedback&t=…`），默认日志格式把整串记下来，读得到日志就能在有效期内直接打开那个玩家的工单 | 反馈站改用不含查询串的格式（`$uri` 代替 `$request`），见 `deploy/nginx.conf.example`；后台站 URL 里没有令牌，保持原样 |
| `events` 表 | 「测试邮件」把收件地址原样永久写入 | 写事件前过 `TicketMail::maskEmailsInText()`，页面上的即时提示仍是完整地址 |
| `storage/logs/app-*.log` | 上游报错常带着密钥回显（`Invalid API key: sk-…`），靠调用点自觉守不住 | `app_log()` 统一过一遍 `redact_secrets()` |

`redact_secrets()` 只抹凭据、保留 IP 和邮箱，这是刻意的：日志里
"哪个 IP 被白名单拒了""哪个 IP 登录失败"是排查时最有用的一条信息。
全面脱敏应该发生在调用点（`TicketMail` 自己会用 `maskAddress`），不在这层搞一刀切。
`tests/run.php` 里有一条断言专门钉住这个取舍。

> 升级提醒：如果你是从 1.12.7 及更早版本升上来的，`deploy/nginx.conf.example`
> 里的日志格式不会自动应用到已有站点。手动给反馈站的 `access_log` 加上
> `mcfix_noquery` 格式即可（配置片段见该文件顶部）。在此之前，历史日志里
> 已经记下的令牌会在有效期内仍然可用。

MOD 分发的四重限制（这是唯一会把文件发给玩家的通道）：

1. 文件只能由管理员上传，或 Agent 从服务端 mods 目录取回，玩家无法指定任意路径
2. Agent 侧只允许 `mods/` 目录下的 `.jar`，按归一化名匹配，单文件 ≤ 64 MB。
   （早期版本连 `plugins/` 一起扫，那是错的 —— 插件是纯服务端组件，客户端永远不需要，
   列出来等于告诉玩家这台服装了什么。）
3. 玩家要的组件名必须出现在自己工单的分析结果里，否则拒绝。`api.php` 的 `mod_request`
   会核对 `client_analysis.needs.components` 与 `suspects` 名单，因此不能当任意文件下载器用
4. 下载链接是签名令牌（`Token::SCOPE_DOWNLOAD`，绑定文件名 + 7 天有效期），
   改文件名无法枚举库里的文件

另外入库时会校验 `PK\x03\x04` 魔数（确认是 zip/jar），Agent 上报时还会比对 sha256。

## 六、输入处理

- 所有输出一律过 `e()`（`htmlspecialchars` + `ENT_QUOTES`）
- 所有数据库查询都是 PDO 预处理，没有字符串拼接（唯一拼接的是 `LIMIT`，且经过 `min/max` 强制整数）
- 玩家 ID 白名单正则：`^[A-Za-z0-9_\x{4e00}-\x{9fa5}]{2,16}$`
- 描述文本先 `mb_substr` 截断再处理换行与控制字符
- JSON 请求体限制 256KB；客户端日志另有 256KB 独立上限
- 后台所有写操作强制 CSRF token 校验（`ConsoleAuth::checkCsrf()`，`hash_equals` 比较）。
  唯一的例外是安装向导的第 2 步（设置管理员密码）—— 那时还没有后台会话，
  它的闸门是"`config/config.php` 不存在"，装完之后这一步就再也走不到了。
  第 3 步（写服务器配置，含 RCON 密码和 Agent 令牌）是要校验 CSRF 的。
- 玩家侧写操作要求 `X-Requested-With: XMLHttpRequest`，配合签名令牌使用
  （玩家侧没有身份，因此不需要 CSRF 令牌 —— 早期版本页面上那个隐藏 `csrf` 字段从来没被校验过，已删除）

## 七、SSRF 与出站请求

系统会主动连出去的场景只有三个，目标都来自管理员的配置，不来自玩家输入：

1. Minecraft 协议握手 / TCP 探测 → `server.host:port`
2. RCON → `server.rcon.host:port`
3. Agent → `panel_url`（由管理员在 MC 机器上配置）

`Net::normalizeHost()` 会拒绝任何带协议头、路径或特殊字符的主机名，只允许域名 / IPv4 / IPv6。

注意：`host` 可以填内网地址（这是必要功能，比如面板和 MC 在同一内网）。
如果后台账号泄露，攻击者可以在管理后台加一台"服务器"指向内网某端口做端口扫描。
所以后台密码强度比什么都重要 —— 这也是为什么它默认带登录失败锁定。

## 八、Agent 侧安全

- 只用 `--once` / 常驻两种模式运行，没有 HTTP 监听端口
- 只通过 `proc_open` 执行三类来源的命令：管理员配置的 `guard.*_cmd`、
  内部拼装的 `systemctl` / `screen` / `tmux` 命令、`tar` 打包命令
- 所有拼进命令的路径都过 `escapeshellarg()`
- 认领任务用乐观锁（`UPDATE ... WHERE status='queued'`），两个 Agent 抢同一条不会重复执行
- 任务带租约和超时，Agent 掉线不会让工单卡死（`Task::reclaim()` 会回收）
- 上传文件时校验 sha256 与大小上限；读取 jar 内的 `mods.toml` / `fabric.mod.json` 只用于识别 mod id
- 建议用独立用户跑 Agent，只给它重启服务端的权限（sudoers 白名单），而不是直接 root

最小权限示例（`/etc/sudoers.d/mcfix`）：

```
mcfix ALL=(root) NOPASSWD: /bin/systemctl restart minecraft-survival, /bin/systemctl status minecraft-survival
```

## 九、已知边界（不打算解决的）

1. 面板机器是唯一信任根。面板被完全控制后，攻击者能改配置、能读数据库里的所有工单与日志。
   请把它当普通 Web 应用来加固（HTTPS、强密码、定期更新 PHP）。
2. Agent 令牌泄露 = 能反复触发白名单内动作、能读取服务端 mods 目录里的 jar。
   建议在后台服务器配置里填 `agent_ip_allow` 限定来源 IP；令牌轮换时点"换成新令牌"填 `__new__`。
3. 开放公开链接等于开放给所有人提交。如果被恶意刷，靠限流 + 缩短有效期 + 必要时轮换密钥来应对。
4. 诊断准确率不是 100%。比如"玩家说卡，但 TPS 正常"，系统会如实告诉你"没检测到异常"，
   然后转人工 —— 这是有意设计，宁可不动手也不要瞎动手。
5. 客户端日志解析是特征匹配，不是万能的。遇到没覆盖的报错会明确说"需要完整崩溃报告"
   或"转人工"，不会硬编一个结论。
6. 出网请求的 TLS 校验默认开启。只有管理员在服务器配置里显式勾选"跳过 HTTPS 证书校验"
   才会关闭，勾了之后面板 API 密钥和日志内容就可能被中间人看到或篡改。
7. `guard.*_cmd` 是"可信本地配置"的逃生门。Agent 会原样执行管理员写在
   MC 机器 `config.php` 里的自定义命令；面板下发的任何内容都进不到这条路径上。

## 十、部署检查清单

上线前逐条打勾：

- [ ] 网站运行目录已指向 `public/`（不改的话 SQLite 库和 `config.php` 可能被直接下载）
- [ ] 用的是 HTTPS，且证书有效
- [ ] 后台口令 ≥ 16 位随机字符，没有在聊天记录/工单里出现过
- [ ] `admin.ip_allow` 填了（至少填你自己的常用网段）
- [ ] `trusted_proxies` 与你的 Nginx 配置匹配（不确定就留空）
- [ ] 计划任务里填的是 `bin/php` 而不是 `php-fpm`
- [ ] `config/config.php` 权限 640，属主与 FPM 运行用户一致
- [ ] `php bin/mcfix.php doctor` 全绿
- [ ] 通知渠道点过「发送测试」并真的收到了
- [ ] 备份任务用的是 `sqlite3 ... ".backup ..."` 而不是 `cp`
